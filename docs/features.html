Assertion System

post-request

assertions map

Per-field assertion rules using a shorthand map. Supports all operators below. Each field can have multiple operators. Conditional logic via when.

  • Use soft: true per-rule to log warning instead of failing
  • Use when: "expression" to conditionally skip
  • Global softFail: true applies soft behavior to all assertions

keysToFind

Simple key existence check. Specify a dot-notation path — the engine walks the response body and confirms the key exists (or is absent with ! prefix).

assertions map example
assertions: {
  "data.id":     { exists: true, type: "number" },
  "data.email":  { matches: "@" },
  "data.score":  { gte: 0, lte: 100 },
  "data.name":   { minLen: 1, maxLen: 100 },
  "data.active": {
    eq: true,
    soft: true,   // warning only
    when: "ctx.response.code === 200"
  },
  "data.items":  { type: "array", minLen: 1 },
  "error":       { absent: true },
},

keysToFind: ["data.id", "data.name", "!error"],
exists

Key exists in response

absent

Key must NOT be present

eq

Strict equality

ne

Not equal

gt

Greater than (number)

gte

Greater than or equal

lt

Less than (number)

lte

Less than or equal

type

typeof check

minLen

Min string/array length

maxLen

Max string/array length

includes

String/array includes

matches

Regex or substring match

soft

Log warning, don't fail

when

Conditional skip expression

absent

Must not exist

assertShape · assertOrder · assertUniquev3.6v3.8

post-request

assertShape — structural type check

Quick one-liner per field: declare the expected type. Options:

  • "string" "number" "boolean"
  • "object" "array"
  • "absent" — field must NOT exist
  • "any" — field must exist, any type

assertOrder — verify sort direction

Checks that an array is sorted by a field in the given direction ("asc" or "desc"). Specify type: "number" or "string".

assertUnique — no duplicatesv3.8

Checks that all values in an array (or sub-field values) are unique. Set by to check a nested field (e.g. "id").

Shape + Order + Unique
assertShape: {
  "data":        "object",
  "data.id":     "number",
  "data.name":   "string",
  "data.items":  "array",
  "data.active": "boolean",
  "error":       "absent",
  "meta":        "any",
},

assertOrder: {
  path:      "data.items",
  by:        "price",
  direction: "asc",
  type:      "number",
},

assertUnique: {
  path: "data.items",
  by:   "id",   // check item.id uniqueness
},

assertEach — array item validationv3.5

post-request

Per-item rule validation

Validates every element of an array against a set of rules. Same operator syntax as assertions map. Supports minCount / maxCount for array length, and per-rule soft mode.

Global softFail: true makes all rule violations non-fatal.

assertEach
assertEach: {
  path:     "data.products",
  minCount: 1,
  maxCount: 200,
  rules: {
    "id":       { type: "number", gt: 0 },
    "name":     { type: "string", minLen: 1 },
    "price":    { gte: 0 },
    "category": { exists: true },
    "active":   {
      eq: true,
      soft: true,  // warn only per item
    },
  }
},

assertHeaders — response header assertions

post-request

One entry per header

An array of entries, each identified by name. An entry without a name is skipped. Unless it is an absence check, every entry first asserts the header exists and is a non-empty string, then applies whichever matcher you gave it:

  • name alone — the header must be present
  • expect: "substring" — the value must contain that string
  • expect: v => … — predicate must return true
  • equals: "v2" — exact value match
  • absent: true — the header must NOT be there
  • label — test name; defaults to the header name

Each entry is its own pm.test

absent: true short-circuits — no existence check runs alongside it, and an empty value counts as absent. equals takes precedence when both equals and expect are given, and is compared as a string. A predicate that throws is treated as a failed check, not as a broken run.

The predicate form is a function, so it only works in a JS override block — not in the JSON hephaestus.defaults. Verdicts also land in ctx._meta.results.headers, where plugins can read them.

assertHeaders
assertHeaders: [
  // exists and is non-empty
  { name: "X-Request-Id" },

  // value contains the substring
  { name: "Content-Type", expect: "application/json" },

  // exact match
  { name: "X-Api-Version", equals: "v2" },

  // must NOT be present
  { name: "X-Powered-By", absent: true },

  // predicate + custom test label
  {
    name:   "X-RateLimit-Remaining",
    label:  "Rate limit not exhausted",
    expect: v => Number(v) > 0,
  },
],

Snapshot Regression Testing

post-request

How it works

On first run, response body is saved as a baseline in a collection variable. On subsequent runs, the current response is compared against that baseline.

  • strict — exact deep equality
  • non-strict — structure & types only (ignores new keys)
  • ignorePaths — skip dynamic fields (timestamps, IDs)
  • checkPaths — only compare specific sub-paths
📸 Open Snapshot Viewer →
snapshot config
snapshot: {
  enabled:     true,
  mode:        "non-strict",
  ignorePaths: [
    "data.updatedAt",
    "data.requestId",
    "meta.timestamp"
  ],
  checkPaths: ["data.status", "data.type"],
  record: false,  // set true to force-rewrite the baseline (snapshotRecord)
},

Logging & softFailv3.8

global config

logLevel: "silent"

No console output. Only CI JSON if ci: true. Good for data-driven runs with thousands of iterations.

logLevel: "minimal"

Single-line summary per request: method, URL, status, time. Compact output for watch mode or large test suites.

logLevel: "normal"

Default. Full bordered summary box with response preview, all assertion results, saved variables.

logLevel: "verbose"

Normal + response headers. Useful for debugging auth, CORS, and caching issues.

softFail: true

Global flag. All assertion failures log as warnings instead of failing the Postman test. Overrides per-rule soft.

ci: true

Outputs structured JSON to console alongside human-readable output. Consumed by ci-to-junit.js.

init --demo — a runnable offline demov4.0

CLI · init.js

See it run before you configure anything

One non-interactive command scaffolds a directory holding a collection, an environment, and a README. The collection carries its own snapshots inside hephaestus.snapshots, so hephaestus mock serves those recorded responses back and Newman runs green — no account, no API key, no network.

  • 5 requests, 35 assertions, all green — including the one that asserts a 404
  • Wired to the real engine, not a simplified copy — every request is copy-pasteable into a real collection
  • The whole test is the override block at the top of the Tests tab; the line under it evaluates the engine
  • Writes to hephaestus-demo/ by default; pass a directory to change it, --force to overwrite

One headline feature per request

  • 1. Health check — expectedStatus: the smallest possible test
  • 2. List products — assertShape, assertEach, assertOrder, maxResponseTime
  • 3. Create product — assertions plus varsToSave into a collection variable
  • 4. Get product — snapshot in structural mode
  • 5. Missing product — a negative test: the 404 is the expected result, so the run stays green because the test says so, not because nothing was checked

Demo paths are deliberately static: mock matches {{id}} / :id segments literally, so a templated path would register the route with the braces still in it.

init --demo
# scaffold it — nothing to answer, nothing to sign up for
npx hephaestus init --demo

# terminal 1 — serve the recorded responses
hephaestus mock hephaestus-demo/demo-collection.json -p 4010

# terminal 2 — run the tests against it
newman run hephaestus-demo/demo-collection.json \
  -e hephaestus-demo/demo-environment.json

# → 5 requests, 35 assertions, 0 failures

# written:
#   hephaestus-demo/demo-collection.json
#   hephaestus-demo/demo-environment.json
#   hephaestus-demo/README.md

# then feed the run into the rest of the CLI:
newman run … -r json --reporter-json-export run.json
hephaestus summary run.json
hephaestus report  run.json demo-report.html
hephaestus docs    hephaestus-demo/demo-collection.json -o demo-api.md

Localization — locale ru · env3.9

global config

One engine, two languages

The locale setting selects the language of every user-facing string the engine emits: generated test names, console logs, error messages, and status labels.

  • "ru" — default. Byte-identical output to prior releases.
  • "en" — the exact same engine, rendered in English.

Nothing about assertions or request behaviour changes — only the text you read. Defined in setup/defaults.json, resolved through the shared i18n catalog.

Why default "ru"

Existing suites keep their exact wording — test IDs, snapshots, and log-scraping stay stable across the upgrade. Opt into English by setting a single field.

locale
// setup/defaults.json (or per-request override)
locale: "ru",   // default — unchanged output

// switch the whole engine to English:
locale: "en",

// affects test names, logs, errors, status labels:
//   ru → "🟢 Статус: 200 — Успешно"
//   en → "🟢 Status: 200 — OK"

Security Auditv3.9

post-request

Response hardening checks

Opt-in module (enabled: false by default). When on, each check emits its own pm.test so failures surface individually.

  • requireHeaders — security headers that must be present
  • forbidHeaders — headers that must NOT leak (server, tech fingerprints)
  • forbidBodyPatterns — strings that must not appear in the body (stack traces, DB errors)
  • checkCors — flags a wildcard Access-Control-Allow-Origin combined with Allow-Credentials

Sensible built-in defaults

When enabled without lists, the engine applies OWASP-style defaults: requires HSTS, CSP, X-Frame-Options, X-Content-Type-Options; forbids server, x-powered-by, x-aspnet-version; and scans the body for SQLSTATE, stack traces, ORA-0, and MySQL warnings. Default { enabled: false, checkCors: true }.

securityAudit
securityAudit: {
  enabled:   true,
  checkCors: true,   // wildcard ACAO + credentials
  requireHeaders: [
    "strict-transport-security",
    "content-security-policy",
    "x-frame-options",
    "x-content-type-options",
  ],
  forbidHeaders: [
    "server", "x-powered-by", "x-aspnet-version",
  ],
  forbidBodyPatterns: [
    "SQLSTATE", "stack trace", "ORA-0",
  ],
},
// each check → its own pm.test

snapshotRecord — force-rewrite baselinev3.9

post-request

Rewrite a snapshot in one run

When an endpoint intentionally changes, you need a fresh baseline. Set snapshot.record: true (or top-level snapshotRecord: true), run once, then remove the flag.

  • Ignores the existing snapshot entirely
  • Writes the current response as the new baseline
  • Stored in the collection-vars backend

Snapshot storage

snapshot.storage defaults to "collection-vars", the only backend that works offline. "postman-api" is unavailable offline — the engine warns once and falls back to collection-vars automatically.

snapshotRecord
// Step 1 — force a new baseline this run:
snapshot: {
  enabled: true,
  record:  true,   // rewrite baseline, ignore old
  storage: "collection-vars",
},

// or the top-level shorthand:
snapshotRecord: true,

// Step 2 — run once.
// Step 3 — remove the flag; back to compare mode.

SLA Percentiles — summary --slav3.9

CLI · summary.js

Latency percentiles & a hard gate

The summary tool now reports p50 / p90 / p95 / p99 response times across the run. Pass --sla=<ms> to turn it into a gate.

  • Exits 1 when p95 exceeds the budget
  • Failed / no-response executions are excluded so they don't deflate percentiles
  • Drop it into CI to fail builds on latency regressions
summary --sla
# percentiles in the summary output
node scripts/summary.js results.json

# gate the run: fail if p95 > 800ms
node scripts/summary.js results.json --sla=800

# → Response time  p50 120ms  p90 410ms
#                  p95 690ms  p99 1.2s
# → SLA OK: p95 690ms <= 800ms  (exit 0)

OpenAPI / Swagger Importv3.9

CLI · openapi-import.js

Spec → Hephaestus collection

Turn an existing API spec into a ready-to-run collection. Reads OpenAPI 3.x and Swagger 2.0 (JSON, or a common YAML subset).

  • One request per path + method
  • expectedStatus pre-filled from the spec's 2xx responses
  • Response schema pre-filled from the spec's schemas
  • Start asserting immediately, no hand-wiring
  • --negative also generates error-path tests

--negative only generates cases the spec lets it actually trigger — withheld auth, a substituted id, an emptied required body, a dropped required parameter. A spec that declares a 400 does not say what makes a request invalid, so no test is invented for it. Each negative request differs from the happy path by exactly one mutation.

openapi
# OpenAPI 3.x or Swagger 2.0 → collection
node bin/hephaestus.js openapi openapi.json

# YAML subset also accepted
node bin/hephaestus.js openapi swagger.yaml

# plus error-path tests
node bin/hephaestus.js openapi openapi.json --negative

# each generated request comes with:
#   expectedStatus  (from 2xx responses)
#   schema          (from spec component schemas)
#
# --negative adds a "<tag> — negative" folder:
#   no auth        401/403   (auth disabled in pre-request)
#   unknown id     404       (path parameter substituted)
#   empty body     400/422   (required body sent as {})
#   missing <p>    400/422   (required query parameter dropped)

extraKeys — allowlist your own config keysv4.0

global config

The typo-guard, and its escape hatch

Every top-level key of a request's override is checked against the list of options the engine knows. An unrecognised key used to be silently ignored — a misspelled option just looked like a feature that did not work. Now it warns, with the nearest known key suggested:

  • Default — ⚠️ Unknown override key: "snapshsot" — did you mean "snapshot"?
  • strictMode: true — a failing pm.test instead, so CI blocks on the typo
  • Warnings are muted at logLevel: "silent"; the strict failure is not

extraKeys turns that guard off per key

Third-party plugins read their settings off ctx.config, which means their keys live in your config — where the engine has never heard of them. List them in extraKeys and both the warning and the strict failure go away for exactly those names.

Read from the merged config, so it works from hephaestus.defaults (covering the whole suite) or from the override itself. A non-array value is ignored. The engine still never reads the listed keys — it just stops complaining about them.

strictMode + extraKeys
// hephaestus.defaults — strict for the whole suite
{
  "strictMode": true,
  "extraKeys": [
    "budgetMs", "budgets",
    "budgetSoft", "budgetWarnAt"
  ],
  "budgetMs": 800
}

// or declared and used in the same override
const override = {
  extraKeys: ["piiRedact", "piiSoft"],
  piiRedact: true,
  piiSoft:   false,
};

// without extraKeys, under strictMode:
//   🚫 strictMode: unknown override key(s)

Plugin Gallery — gallery/plugins/v4.0

post-request · plugins

Drop-in, zero dependencies, no engine fork

Four working plugins plus a commented skeleton. Each is a single file you paste into a collection variable and register in the collection's Pre-request script — no build step, no fork.

  • The descriptor key is post, and its value is the name of the variable holding the code, not the code itself
  • Plugins run once per request, second to last in the pipeline — after securityAudit, before logger.summary
  • Running there is what makes them possible: every assertion verdict is already in ctx._meta.results, and ctx.config is still live
  • If retryOnStatus fires, the pipeline stops before plugins and they do not run that iteration
  • A throw inside a plugin becomes a failing test named after it; the remaining plugins still run

Gallery keys need extraKeys

Every gallery plugin reads its settings off ctx.config, so its keys live in your hephaestus.defaults or in a request's override. None of them are keys the engine knows about — they are not in KNOWN_KEYS, which covers only the engine's own options plus the shipped first-party plugins.

So each one warns by default, and fails the run under strictMode: true. Declare them with extraKeys and both go away.

install a gallery plugin
// 1. Paste the file's text into a collection variable:
//    hephaestus.plugin.budget → <contents of response-budget.js>

// 2. Register it in the collection Pre-request script:
pm.collectionVariables.set('hephaestus.plugins', JSON.stringify([
  { name: 'response-budget',  post: 'hephaestus.plugin.budget' },
  { name: 'timing-histogram', post: 'hephaestus.plugin.histogram' },
  { name: 'pii-redactor',     post: 'hephaestus.plugin.pii' },
]));

// 3. Configure through override — every key lands in ctx.config,
//    and must be declared when strictMode is on:
const override = {
  extraKeys: ['budgetMs', 'budgets', 'piiSoft', 'csvPrint'],
  budgetMs: 800,
  budgets:  { 'Login': 2000, 'Health check': 200 },
  piiSoft:  false,
  csvPrint: true,
};

// Plugins that accumulate state (timing-histogram, csv-metrics)
// use collection variables, which persist between runs — clear
// them at the top of the same Pre-request script:
if (!pm.info.iteration) {
  pm.collectionVariables.unset('hephaestus.plugin.timings');
  pm.collectionVariables.unset('hephaestus.plugin.csvRows');
}

Fails the run when a response misses its latency budget. Per-request budgets, soft mode, and a warning band before the hard limit.

budgetMs · budgets · budgetSoft · budgetWarnAt

📊 timing-histogram.js

🕵️ pii-redactor.js

Finds credential- and PII-shaped values in the response, reports them masked, and registers their field names so the engine summary redacts them too.

📑 csv-metrics.js

Appends one CSV row per request — timing, size, and every module's verdict — and prints the whole table between cut markers at the end of the run.

csvVar · csvMaxRows · csvUrl · csvPrint

📄 _template.js

Commented skeleton documenting every surface a plugin can touch: ctx.config, ctx.request, ctx.response, ctx.api, ctx.iteration, ctx._meta, _override. Copy, rename, delete the rest.

⚠️ Two things that trip up first plugins

ctx.api carries only get/find/all/count/save — status and timing live on ctx.response. And ctx._meta.results entries use ok, not passed; modules that did not run leave their slot empty, so guard before reading.

New in 4.0v4.0

engine + CLI

Engine — all opt-in, all off by default

  • graphql — GraphQL answers 200 even with an errors[] array; assert noErrors, errorCount/errorContains for negative tests, and dataShape under data.*.
  • snapshot.mode: "structural" — compares the response shape (leaf path → type) and ignores values, so volatile timestamps and ids stop causing false diffs while a field added, removed or retyped still fails.
  • retryOnStatus.respectRetryAfter — honours the server's Retry-After, waiting up to retryAfterCapMs and refusing to hammer past it.
  • maxBytes — a response-size budget; the maxResponseTime for payload size.
  • securityAudit v2 — cookieFlags, checkJwt (rejects alg:none and expired tokens) and requireNoStore.
  • Override typo-guard — an unknown key warns with a "did you mean"; strictMode: true fails the run so CI blocks on a typo.

Any locale is now selectable

Locale selection was hardcoded to ru/en, so a fully translated third language could never be used. Any locale the catalog carries is now selectable, and npm run check:locales validates a contribution — completeness, parameter parity, argument types, status coverage.

CLI — gates and local tooling

  • doctor — pre-flight: engine integrity, version drift, config sanity.
  • coverage --spec — % of an OpenAPI spec your collection covers, with a --min gate.
  • flaky — assertions that flap across repeated runs (--fail-on-flaky).
  • trends + summary --history — pass-rate and p95 sparklines from a local run log.
  • bench — what the engine actually costs per request (~1.6 ms), with a --max-ms budget.
  • mock — replay saved snapshots as a local API.
  • generate — interactive wizard that prints a ready-to-paste override.
  • panel — local dev panel: run history, snapshots, defaults editor, docs.

Every gate exits 1 when it trips — see the CI guide.

override
// a few of the new fields
const override = {
    graphql: { noErrors: true },
    snapshot: { enabled: true, mode: "structural" },
    retryOnStatus: {
        statuses: [503, 429],
        respectRetryAfter: true
    },
    maxBytes: 1048576,
    strictMode: true
};
