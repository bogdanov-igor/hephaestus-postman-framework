# ⚒️ Hephaestus: Концепция развития и дорожная карта (Vision & Roadmap)

Этот документ описывает одобренные идеи, техническое видение и новые архитектурные модули для развития автоматизации API-тестирования в фреймворке **Hephaestus**.

---

## 🚀 Общее видение (Vision)
Цель развития Hephaestus — превратить его из набора скриптов в полноценную экосистему для разработчиков и QA-инженеров, которая минимизирует рутинный ручной труд в UI Postman, обеспечивает высокий уровень безопасности тестируемых API, предоставляет удобный CLI-инструментарий и наглядную визуализацию результатов.

---

## 🗺️ Дорожная карта v1 и одобренные модули (статусы на июль 2026)

### 1. Переход на TypeScript & Локальная сборка (Bundling) — ✅ сделано иначе (v3.9): модульный JS + esbuild, без TypeScript
* **Зачем**: Код ядра ([pre-request.js](file:///Users/bogdanov.i.a./Documents/hephaestus-postman-framework/engine/pre-request.js) и [post-request.js](file:///Users/bogdanov.i.a./Documents/hephaestus-postman-framework/engine/post-request.js)) превышает 100 KB. Разрабатывать и рефакторить его на чистом JavaScript без типизации становится сложно.
* **Как это будет работать**:
  * Исходники переносятся на TypeScript (`src/pre-request.ts`, `src/post-request.ts`).
  * Настраивается быстрый сборщик `esbuild`.
  * Команда `npm run build` компилирует и собирает код в оптимизированные JS-бандлы, которые затем обновляются в Postman-коллекции.
* **Удобство**: Автодополнение методов контекста `ctx` (IntelliSense) в VS Code/Cursor и проверка типов на этапе сборки.

### 2. Принудительная запись снапшотов через `snapshotRecord` — ✅ v3.9
* **Зачем**: Сейчас обновление устаревших регрессионных снапшотов требует ручного сброса или переключения глобальных настроек.
* **Как это будет работать**:
  * В конфиг-объект `override` запроса добавляется флаг `"snapshotRecord": true` (или вложенный `"snapshot": { "record": true }`).
  * При отправке запроса движок видит этот флаг, игнорирует старый снапшот, записывает текущий ответ сервера как новый baseline и сохраняет его.
  * После этого флаг убирается.
* **Удобство**: Обновление снапшотов для конкретных эндпоинтов в один клик прямо из UI Postman.

### 3. Интеграция с OpenAPI/Swagger (Автогенератор тестов) — ✅ `scripts/openapi-import.js` (PR #3)
* **Зачем**: Ускорение создания тест-кейсов с нуля. Разработчики пишут OpenAPI-спецификации, и тесты должны рождаться автоматически.
* **Как это будет работать**:
  * CLI-скрипт `scripts/openapi-import.js` считывает файл спецификации `openapi.yaml` или `json`.
  * Скрипт генерирует структуру коллекции Postman (папки, методы, URL).
  * Для каждого запроса автоматически генерируется `override`-конфиг с правильным `expectedStatus`, извлекаются JSON-схемы из OpenAPI и прописываются в параметр `schema`.
* **Удобство**: Генерация готовой коллекции тестов со 100% валидацией структуры данных в один вызов CLI.

### 4. Модуль автоматического аудита безопасности (API Security Audit) — ✅ v3.9 (модуль `securityAudit`)
* **Зачем**: API должно быть не просто функциональным, но и безопасным. Тесты в CI должны блокировать релиз, если найдены базовые уязвимости.
* **Как это будет работать**:
  * В [post-request.js](file:///Users/bogdanov.i.a./Documents/hephaestus-postman-framework/engine/post-request.js) добавляется модуль `securityAudit`.
  * Модуль проверяет:
    * Отсутствие раскрытия версий серверов (заголовки `Server`, `X-Powered-By`).
    * Наличие обязательных защитных заголовков (HSTS, CSP, X-Frame-Options, X-Content-Type-Options).
    * Отсутствие отладочной информации и stack traces в теле ответа (поиск подстрок `SQLSTATE`, `stack trace`, `db error` и т.д.).
    * Небезопасные настройки CORS (передача Credentials при Wildcard Origin).
* **Удобство**: Постоянный фоновый контроль безопасности API на каждом запуске тестов.

### 5. Анализ производительности и SLA — ✅ v3.9 (p50/p90/p95/p99 в summary + `--sla`-гейт)
* **Зачем**: Отслеживание не только единичного времени ответа, но и общей стабильности работы API под нагрузкой или при многократных запусках.
* **Как это будет работать**:
  * Добавление assertions для вычисления перцентилей времени отклика (p95, p99) по результатам итераций Newman.
  * Настройка порогов (SLA) для критических методов.
  * Фиксация фактов деградации времени ответа относительно baseline-снапшотов.
* **Удобство**: Раннее предупреждение о проблемах с производительностью до релиза в прод.

### 6. CLI-Конструктор Overrides — ⏳ в плане v2 (Фаза G), на `node:readline` вместо Inquirer (zero-dep)
* **Зачем**: Сокращение времени на написание JSON-переопределений для новых запросов вручную.
* **Как это будет работать**:
  * Интерактивная консольная утилита `npm run generate-test`.
  * В диалоговом режиме (через Inquirer) задает вопросы: название метода, URL, авторизация, какие переменные сохранить, нужен ли снапшот.
  * На выходе выдает готовый блок кода для вставки в Postman.
* **Удобство**: Быстрый старт для начинающих QA без необходимости помнить синтаксис конфигов наизусть.

### 7. Синхронизация снапшотов с Postman Examples — ✅ `scripts/sync-examples.js` (PR #2)
* **Зачем**: Снапшоты Hephaestus хранятся в скрытой переменной коллекции, что мешает просматривать их в UI Postman.
* **Как это будет работать**:
  * Скрипт `scripts/sync-examples.js` считывает сохраненные снапшоты Hephaestus.
  * Скрипт записывает эти JSON-ответы обратно в файл коллекции как нативные "Example Responses" для каждого запроса.
* **Удобство**: Снапшоты становятся видимыми в UI Postman как примеры ответов, и их можно сразу использовать для запуска стандартного Postman Mock Server.

### 8. Локальная панель разработчика (Hephaestus Dev Panel) — ⏳ в плане v2 (Фаза H, финальная фича)
* **Зачем**: Единое визуальное окно управления вместо разрозненных HTML-файлов и консольного вывода.
* **Как это будет работать**:
  * Утилита запускает легковесный локальный веб-сервер (`npm run dev-panel`).
  * Предоставляет красивый, современный веб-интерфейс (темная тема, плавные переходы, HSL-палитра).
  * **Функционал панели**:
    * Интерактивный Diff Viewer для просмотра различий в упавших снапшотах.
    * Редактор глобальных настроек `defaults.json` и файлов окружения с валидацией.
    * История локальных запусков тестов и просмотр сгенерированных отчетов.
    * Быстрые ссылки на документацию и локальный конструктор оверрайдов.
* **Удобство**: Полный визуальный контроль над состоянием автотестов на компьютере инженера.

## 🧭 Дорожная карта v2 (июль 2026)

Продолжение плана после закрытия большей части v1 (статусы — выше). Сгруппировано по фазам; порядок рекомендуемый, соседние фазы можно частично параллелить.

### Принципы (неизменны)

* **Локально / офлайн / zero-dep**: никаких облаков, бэкендов и ИИ-зависимостей; runtime-зависимостей — ноль.
* Движок остаётся совместимым с sandbox Postman (ES5), собирается esbuild'ом из `engine/src/**`; `pre-request.js`/`post-request.js` руками не правим.
* Каждое поведенческое изменение движка проходит golden-тесты и адверсариальное ревью перед merge.
* `npm publish` — строго последний шаг, после полного наведения порядка.

### Фаза A — Витрина (в работе)

* Добить баннер keel/loft по `BANNER-TODO.md`: cache-bust `?v=3.9`, шапка README.ru, удалить старый `docs/banner.png`.
* Завершить переоформление README (en/ru) и `docs/` (config-reference уже в правке).
* Social preview репозитория — og-картинка из баннера (влияет на каждый шар ссылки).
* GitHub topics и описание репо: `postman`, `newman`, `api-testing`, `qa-automation`, `snapshot-testing`.

### Фаза B — Быстрые победы

* **`hephaestus doctor`** — диагностика окружения и коллекции: движок соответствует `engine/checksums.json`, `defaults` не разъехались с `setup/defaults.json`, версии единые, node ≥ 18, обязательные env-переменные на месте.
* **securityAudit v2** — флаги cookie (`Secure`/`HttpOnly`/`SameSite`), sanity-проверка JWT в ответах (`alg: none`, истёкший `exp`), `Cache-Control: no-store` на auth-эндпоинтах.
* **`maxBytes`** — бюджет размера ответа в `override` (младший брат SLA).
* **`Retry-After`** — `retryOnStatus` уважает заголовок при 429/503.
* **Защита от опечаток** — валидация ключей `override` по словарю: warn в лог, жёсткий fail при `strictMode: true` (сейчас `snapshsot` молча игнорируется).
* **JSON Schema конфига** — `docs/override.schema.json` (+ `$schema` в `defaults.json`): автокомплит и подсветка ошибок прямо в VS Code. Ноль зависимостей.
* **EN-golden** — дозакрыть end-to-end покрытие английской локали (error/edge-пути через newman).

### Фаза C — Демо и красота

* **`hephaestus mock`** — локальный mock-сервер из сохранённых снапшотов (голый `node:http`, матчинг метод+путь): фронтенд работает офлайн против записанного API.
* **`hephaestus init --demo`** — «демо за 60 секунд»: пример-коллекция + mock + зелёный прогон офлайн сразу после клона, без внешнего API.
* **GIF-демо в README** — записанный терминальный прогон (vhs), живой прогон продаёт лучше текста.
* **HTML-отчёт в фирменном стиле** — палитра «огонь→закалка», тёмное поле и типографика баннера; единый визуальный язык с будущей Dev Panel.
* **Фирменный вывод CLI** — единый стиль секций и цветов через голые ANSI-коды, ⚒ в заголовке.
* **Рецепты в доках** — «10 задач — 10 готовых override-блоков»: пагинация, цепочка авторизации, полинг с ретраями и т.д.

### Фаза D — OpenAPI-связка

* **`hephaestus coverage --spec openapi.yaml collection.json`** — процент покрытия путей/методов спеки коллекцией + список непокрытых эндпоинтов (переиспользует YAML-парсер openapi-import).
* **`openapi-import --negative`** — авто-негативные тесты: по required-полям и типам генерировать запросы «без обязательного поля / не тот тип» с `expectedStatus: 400/422`. Rule-based, без ИИ.

### Фаза E — Данные о запусках (грунт под Dev Panel)

* **Локальная история** — summary дописывает одну JSON-строку в `.hephaestus/history.jsonl` за запуск (pass-rate, p95, длительность). Ноль бэкенда.
* **`hephaestus trends`** — спарклайны p95/pass-rate по истории: в терминале + секция в HTML-отчёте.
* **Детектор флаки** — по N прогонам находить «мигающие» ассерты (на базе композитного ключа compare).

### Фаза F — Ядро и техчасть

* **GraphQL-ассерты** — новый модуль: `errors` пуст, `data` не null, обработка partial failures. Ниша почти пустая.
* **Структурный diff снапшотов** — contract-режим: сравниваем типы и наличие полей, значения — нет. Contract-testing без внешних инструментов.
* **Кастомная сборка ядра** — `npm run build:emit -- --modules=…`: собирать движок только из нужных модулей (меньше бандл — быстрее eval на каждый запрос).
* **Бенчмарк оверхеда** — замерить и опубликовать «движок добавляет N мс на запрос», следить за регрессией в CI.
* **Windows-совместимость** — пути/ANSI/line-endings во всех скриптах; windows-runner в собственный CI (аудитория QA массово на Windows).

### Фаза G — Конструктор overrides (§6 из v1)

* `hephaestus generate-test` на встроенном `node:readline` (не Inquirer — сохраняем zero-dep): диалог метод → URL → авторизация → переменные → снапшот → готовый блок `override` для вставки в Postman.

### Фаза H — Dev Panel (§8 из v1, зонтик)

* Локальный сервер `npm run dev-panel`, единый стиль с отчётом: интерактивный diff-viewer снапшотов, редактор `defaults.json` с валидацией по JSON Schema (Фаза B), история запусков и тренды (Фаза E), конструктор (Фаза G), ссылки на доки.
* Делается последней из фич — к этому моменту панели есть что показывать.

* **Галерея плагинов** — `gallery/plugins/`: 3–4 образцовых плагина + шаблон «напиши свой». Самая низкая ступенька для первого контрибьютора.
